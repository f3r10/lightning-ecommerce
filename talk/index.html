CLN and LND are great, but they're daemons you operate separately from your app, and neither ships LSPS2 out of the box — you'd build the client side yourself. Breez SDK is excellent but optimized for mobile wallets, and its default key-custody model (Greenlight) isn't what you want for a merchant-owned node. ldk-node is a Rust library you embed directly in your service — no separate process, no RPC boundary — and LSPS2 client support is native. Be upfront about the tradeoff: it's pre-1.0, so APIs shift between releases, but because it's Rust every breaking change surfaces as a compile error, not a silent runtime failure — pin a git rev and upgrade deliberately. The Protocol
LSPS2 in Two Messages (bLIP-52)

Over LSPS0 — the existing Lightning peer connection. No new network connection.

🧑 Client
🏦 LSP
① lsps2.get_info
fee schedule returned
② lsps2.buy
phantom SCID returned

Phantom SCID → encoded as a route hint in the BOLT11 invoice

LSPS2 rides on top of LSPS0, which is just a peer-messaging layer over an existing Lightning connection — no new sockets, no new transport, it's a message type on a connection you already have. The negotiation is exactly two round trips: get_info tells the client what the channel will cost, buy locks that price in and gets back a short channel ID that doesn't correspond to a real channel yet. That phantom SCID gets embedded as a route hint in the invoice the client hands to the payer — from the payer's perspective it looks like a completely normal channel to route through. Target about 3 minutes.
The Payment Flow
From Phantom SCID to Open Channel
💳 Payer
🏦 LSP
🏪 Merchant Node
① HTLC via phantom SCID

② Holds HTLC
prepares funding tx — does NOT broadcast

③ Opens zero-conf anchor channel

ChannelPending  →  ChannelReady

④ Forwards HTLC, minus fee

PaymentReceived → reveals preimage

⛓ Broadcasts funding tx NOW

✅ Settled. No on-chain cost if no payment arrives — the channel only exists because a payment paid for it.

This is the core mechanic of the whole talk, so slow down here and click through the five steps. (1) The payment doesn't wait for the channel — the channel waits for the payment. The payer's wallet routes toward a route hint pointing at a phantom SCID. (2) The LSP is now holding real value as collateral and prepares, but does not broadcast, the funding transaction — nothing on-chain yet, so no cost if this never completes. (3) Because the LSP controls that unbroadcast funding tx, it can safely open a zero-conf anchor channel straight to the merchant — both sides see ChannelPending then ChannelReady before anything is on-chain. (4) The LSP forwards the originally-held HTLC minus its fee; the merchant's node fires PaymentReceived and reveals the preimage, proof the payment happened. (5) Only now, with proof the channel is worth funding, does the LSP broadcast the funding transaction. Punchline: this inverts "provision liquidity, then hope someone pays" into "get paid, then provision liquidity" — that's what makes zero-upfront-cost self-custody possible. Target about 3 minutes total across the five clicks.

node-service is a small Axum HTTP service that sits in front of ldk-node — it exposes exactly two endpoints an application needs. Invoice creation is a single call, receive_via_jit_channel, which does the get_info/buy negotiation with the LSP under the hood so the caller never touches LSPS2 directly. Configuration is deliberately boring: numbered environment variables let you register multiple LSPs, and ldk-node's internal fee comparison picks the cheapest one at invoice time — no extra code required on our side. Target about 2 minutes.
Under the Hood
Code: Registering LSPs
for (node_id, address, token) in parsed_lsps {
    builder.add_liquidity_source(node_id, address, token, true);
}
let node = builder.build(entropy)?;

One call per LSP

Multi-LSP fee comparison is automatic — no application code needed to compare offers.

This is the entire multi-LSP setup — loop over your configured LSPs and call add_liquidity_source once for each, then build the node. ldk-node handles querying every registered LSP's fee schedule and choosing the cheapest one when an invoice is actually requested, so there's no comparison logic anywhere in our application code. The trailing boolean marks it as a JIT-channel-capable source. Keep the emphasis on how little code this is.
Under the Hood
Code: The Event Loop
match node.next_event_async().await {
    Event::ChannelPending { channel_id, .. } => {
        jit_channels_pending.lock().unwrap()
            .insert(channel_id);
        node.event_handled()?;
    }
    Event::ChannelReady { channel_id, .. } => {
        jit_channels_pending.lock().unwrap()
            .remove(&channel_id);
        node.event_handled()?;
    }
    // ...
}

HashSet<ChannelId>, not a counter

A counter would decrement on any payment received — even one over an existing channel — incorrectly clearing the JIT-opening state.

next_event_async gives a typed, awaitable event stream instead of polling or callbacks — match on the variant and call event_handled to acknowledge it, which is how ldk-node knows it's safe to persist state and move on. The detail worth calling out: jit_channels_pending is a HashSet<ChannelId>, not a counter. If it were a counter, any PaymentReceived event — including a normal payment over a channel that already existed — would decrement it and could incorrectly clear the "channel is opening" state. Keying by channel ID means only the specific pending channel gets removed when it becomes ready.

Sticky flag

Once the banner shows, it holds until succeeded.

Prevents a visible gap between ChannelReady firing and the payment status actually flipping to confirmed — without it the UI would flicker back to neutral.

The backend derives a synthetic opening_channel status by checking whether any channel is currently pending while the order itself is still marked pending — it's a cheap read of the same HashSet from the event-loop slide, not a new state machine. On the frontend, setChannelOpening only ever gets set true or false in these two places — that's deliberate, it's a sticky flag. Without it there'd be a visible gap between the channel becoming ready and the payment status flipping to succeeded, where the UI would flicker back to neutral before showing success.

Roadmap
What's Next

🧾 BOLT12 Static Offers

Merchant publishes once. JIT channel still opens on first payment — BOLT12 changes invoice negotiation, not the liquidity model.

🔧 rust-lightning PR #4463

BOLT12 blinded paths carrying LSPS2 SCIDs.

🪝 LSPS5 Webhooks

Hold HTLC → wake service → claim payment. A serverless merchant node.

🌉 Ark / bark

bark 0.3.0 users can already pay our BOLT11 invoices today.

BOLT12 is the natural next step but it's worth being precise about what it changes: it replaces per-payment invoice generation with a static offer the merchant publishes once, but the underlying JIT channel mechanism from earlier in the talk is untouched — that work is tracked upstream in rust-lightning PR #4463, which threads LSPS2 SCIDs through blinded paths. LSPS5 webhooks point toward an even more interesting future: a merchant node that doesn't need to run continuously, waking only when a webhook fires to claim a held payment. Ark interop isn't hypothetical — bark 0.3.0 can pay these BOLT11 invoices right now. Target about 1 minute.
